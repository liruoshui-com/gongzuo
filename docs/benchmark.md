# 怎样验证「更快、更省、更好」

**状态：方案准备中，尚无真实模型对照结果。**示例 JSON 全部使用 `null` 表示未测量。

## 核心问题

共作是否能让普通用户在保留成果质量和个人特点的前提下，用更少的总 token、更短时间和更少返工完成任务？

## 第一轮规模

准备 9 个固定任务：3 个基于材料的研究判断、3 个 CSV 办公处理、3 个个性化 HTML 工具。每个任务包含相同输入、参考答案或功能检查、2 项个人要求和可重复的修改反馈。

比较三个方法：普通直接聊天、固定专业提示词、共作。使用相同模型版本、材料、工具权限、输出限制和重试上限。每题每组运行 2 次，共 54 次，作为初步实验；后续再扩大样本和招募新手。

如果某组没有同等工具，应单独报告「产品整体比较」，不能称为流程本身节省的严格对照。最新信息任务固定资料快照或记录检索日期、查询和来源。

## 质量与个人特点

预先约定盲评规则：正确性 40 分、任务完整度 25 分、个人要求落实 20 分、可使用与可编辑性 15 分。初步合格标准设为至少 80 分且无关键错误，三组一致。

CSV 与预设真值核对；产品实际测试主要操作、刷新保存和导出。个人要求应能检查，例如「允许补记历史记录」或「给出三条可追溯结论」，不能只评价“看起来像我”。

## 消耗必须覆盖完整任务

记录所有澄清、生成、检查、失败、重试和反馈后的修改：

- 服务商返回的输入与输出 token；缓存、推理为明细，不重复叠加。
- 执行总时间、用户实际操作时间、等待时间。
- 人工修改轮数、关键失败和最终验收情况。
- 模型版本、接口、工具条件、参数、时间及数据来源。

缺失用量必须标记为未知；不以 0 补齐。不同模型的 token 计数不能直接解释为同等金额；跨模型比较同时保留服务商、价格日期和实际账单口径。

同时报告：

1. **合格率**以及个人要求分数。
2. **全部尝试 token 总和 ÷ 合格任务数**，使失败消耗进入成本；没有合格任务时该比值不可计算。
3. 合格结果的耗时分布和返工次数，附逐题数据与失败案例。

只有质量和个人要求得分没有下降时，才讨论节省。小样本先报告初步结果，不能扩大成普遍有效的百分比。
